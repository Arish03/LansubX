# Lansub X: Product Requirements Document (PRD)

| | |
|---|---|
| Product | Lansub X, industrial IoT platform |
| Version | 0.1 (MVP) |

## 1. Overview
Lansub X collects data from industrial machines and IoT devices, stores it, shows it live, raises alarms and sends commands back. It supports machines that cannot speak MQTT through gateways (Modbus, OPC UA, LoRa) and devices that speak MQTT directly (ESP32, sensor controllers, PLCs).

## 2. Problem
Factories and workshops have machines with different protocols and no single place to see them. Existing tools are expensive, hard to set up, or lock users into one vendor. Staff learn about faults late.

## 3. Goals and non-goals
**Goals:** unified live view of mixed-protocol devices; reliable alarms; two-way control; simple setup using default templates; secure by default.
**Non-goals (v0.1):** AI analytics, video, edge compute, billing, multi-organization tenancy, native mobile app.

## 4. Users and roles
| Role | Can do |
|---|---|
| Admin | Everything, manage users |
| Engineer | Create/edit devices, rules, gateways; ack alarms; send commands |
| Operator | View; ack/resolve alarms; send commands |
| Viewer | View only |

## 5. Functional requirements
Priority: **P0** must for MVP, **P1** should, **P2** later.

### 5.1 Authentication and users
| ID | Requirement | Priority |
|---|---|---|
| FR-A1 | First registered user becomes admin; later registration closed or admin-only | P0 |
| FR-A2 | Login with email and password, returns JWT | P0 |
| FR-A3 | Passwords stored with bcrypt | P0 |
| FR-A4 | Role-based access on every protected route | P0 |
| FR-A5 | Admin can list users and change roles/active flag | P0 |
| FR-A6 | Token refresh and login rate limit | P1 |
| FR-A7 | httpOnly cookie issued by backend | P1 |

### 5.2 Devices and templates
| ID | Requirement | Priority |
|---|---|---|
| FR-D1 | CRUD devices; kinds: esp32, sensor_controller, plc, modbus, opcua, lora | P0 |
| FR-D2 | Unique `device_key` (`dev_` + 12 hex) generated by the backend | P0 |
| FR-D3 | Direct kinds get an MQTT secret shown once; only a hash is stored | P0 |

| FR-D7 | Devices scoped to their owner | P0 |

### 5.3 Ingestion

## 6. Non-functional requirements
| ID | Category | Requirement |
|---|---|---|
| NFR-1 | Latency | Message to database < 1 s; to browser < 2 s (local network) |
| NFR-2 | Throughput | At least 100 devices at 5 s interval (about 20 messages/s) on one modest server |
| NFR-3 | Availability | Components auto-restart; worker, gateway and clients reconnect without manual action |
| NFR-4 | Security | Broker auth + ACL; JWT; bcrypt; owner scoping; CORS allow-list; no secrets in git |
| NFR-5 | Transport security | HTTPS and MQTT TLS (8883) in production |
| NFR-6 | Data | Daily backup with tested restore; configurable retention |
| NFR-7 | Observability | Structured logs for worker, gateway, API |
| NFR-8 | Maintainability | Alembic migrations, tests for core paths, pinned dependencies |
| NFR-9 | Usability | Setup of a device in under 5 minutes with a default template |
| NFR-10 | Compatibility | Current Chrome, Edge, Firefox; tablet width |

## 7. Data requirements
Entities: User, Gateway, Device, DeviceTemplate, Telemetry, AlarmRule, Alarm, Command. Telemetry is stored one row per (device, metric, timestamp). See `ARCHITECTURE.md` for the schema.

## 8. Default data (starting templates)
These are Lansub X templates, not protocol standards. Real values depend on the machine.
| Kind | Defaults |
|---|---|
| Modbus | TCP 502, slave 1, 5 s, holding registers 0-6 (temperature x0.1, pressure x0.01, flow_rate x0.1, motor_speed x1, motor_current x0.01, vibration x0.01, power x0.1), coils running/fault |
| OPC UA | `opc.tcp://<host>:4840`, no security for testing, 5 s, namespace 2 nodes Temperature, Pressure, FlowRate, MotorSpeed, MotorCurrent, Vibration, Running, Fault |
| LoRa | ChirpStack, class A, 10 min, IN865, fields temperature, humidity, battery, rssi, snr |
| ESP32 | 5 s: temperature, humidity, rssi, uptime, free_heap |
| Sensor controller | 5 s: temperature, pressure, level, input_1, input_2, output_1 |
| PLC (MQTT) | 1-5 s: running, fault, cycle_count, cycle_time, motor_speed, motor_current |

## 9. Integrations and interfaces
| Interface | Detail |
|---|---|
| MQTT | Topics and payloads in `ARCHITECTURE.md` |
| REST | JSON over HTTPS, JWT bearer, OpenAPI at `/docs` |
| WebSocket | `/ws?token=` (ticket-based auth later) |
| ChirpStack | MQTT uplinks with decoded `object` |

## 10. Assumptions and constraints
- ChirpStack decodes LoRa payloads to JSON before they reach Lansub X.
- Values are numeric (booleans become 1/0).
- One owner per device in v0.1.
- Single-server deployment with Docker Compose.
- Direct-device provisioning is manual (`add_mqtt_user.sh`) until the Dynamic Security plugin is added.

## 11. Risks
| Risk | Mitigation |
|---|---|
| Worker not started | Acceptance test checks "MQTT worker connected" |
| Provisioning step forgotten | Wizard warning; Dynamic Security later |
| Telemetry growth | Retention now, Timescale later |
| Library drift | Pin versions |
| Scope creep | Scope guard in `MVP.md` |

## 12. Success metrics
- All MVP acceptance criteria pass.
- Time to add and see a first device under 5 minutes.
- Zero cross-user data leaks in tests.
- 24 hour soak test with simulators: no worker crashes, no data loss after broker restart.
